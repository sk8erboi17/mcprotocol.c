# Minecraft Java 26.2 (protocol 776) → 26.3 (protocol 777): wire-format delta

Scope: everything a protocol-777 client has to change compared with a 776 client, with a source citation for each
claim. Primary source: ViaVersion **5.12.0** (the `v26_2to26_3` protocol, which converts a 26.2 server stream into
a 26.3 client stream). Cross-check: PacketEvents **v2.14.0** (its version branches for `ServerVersion.V_26_3`).
Registry ID lists were decoded from the ViaVersion jar's mapping NBT and compared against the PacketEvents JSON
registries. Where the two sources agree, the claim is marked ✔✔ (two independent sources). Anything not proven
by source is marked **UNVERIFIED**.

Version numbers: `v26_2 = register(776, "26.2")` and `v26_3 = register(777, "26.3")`
[VV `api/.../protocol/version/ProtocolVersion.java` L97-98].

### How ViaVersion applies handlers (needed to read the citations correctly)
* Before `registerPackets()`, `AbstractProtocol.initialize()` applies *shared registrations* chosen by the
  **server-side** version of the protocol [VV `common/.../api/protocol/AbstractProtocol.java` L105-118;
  `SR/SharedRegistrations.java` L64-90]. For `Protocol26_2To26_3` the server side is 26.2, so the ranges ending at
  `.to(ProtocolVersion.v26_3, …)` apply: `registerEntityPackets1_21_9` [VV `SR/def/DefaultRegistrations.java` L36],
  `registerItemPackets1_21_6` [L54], `registerParticlePackets1_21_9` [L76], `registerComponents26_2` [L93],
  `registerBlockPackets1_21` [L65]. The `…26_3` variants (`registerLogin26_3`, `registerLevelParticles26_3`, …)
  are what a *future* 26.3→x protocol uses to *read* 26.3 – they independently document the 26.3 layout.
* `appendClientbound` adds a handler after the shared one; `replaceClientbound` discards it
  [VV `common/.../api/protocol/AbstractProtocol.java` L153-184].
* Packets without a custom handler whose name is the same on both sides are re-ID'd only (body unchanged)
  [same file L186-213].

## Packet ID tables (confirmation of the pre-established result)

Confirmed by two independent sources ✔✔: ViaVersion enums `CB263`, `SB263`, `CFG263` (ordinal = ID) and
PacketEvents `PRO/packettype/{clientbound/ClientboundPacketType_26_3, serverbound/ServerboundPacketType_26_3,
config/clientbound/ClientboundConfigPacketType_26_3}.java`. A position-by-position comparison of the two (working
`enumcmp.py`) gives the same count (144 / 69 / 21) and the same packet at every ID, apart from naming conventions.
26.2 uses ViaVersion's `ClientboundPackets26_1` / `ServerboundPackets26_1` (26.1 and 26.2 have the same ID table)
[VV `P263` L70, L279-282].

* **Clientbound play** (26.2 has 141 packets, 26.3 has 144): `ADD_TRANSIENT_BLOCK` inserted at **37 (0x25)** [`CB263` L59],
  `POST_EFFECTS` at **83 (0x53)** [L105], `SWING_ANIMATION` at **123 (0x7B)** [L145]. Effect: ids 0-36 stay the same,
  37-81 move up by 1, 82-120 move up by 2, and 121-140 move up by 3. Examples: LOGIN 49→50, MOVE_ENTITY_POS 53→54, RESPAWN 82→84,
  SET_ENTITY_DATA 99→101, SYSTEM_CHAT 121→124, UPDATE_ADVANCEMENTS 130→133.
* **Serverbound play** (69 packets in both): `PUNCH` inserted at **46 (0x2E)** [`SB263` L68]. 26.2 `SPECTATE_ENTITY` (62) is renamed
  `SPECTATOR_ACTION` (63) [L83]. `SWING` (26.2 id 63) **no longer exists**. Effect: ids 0-45 stay the same, 26.2 ids 46-62 move up by 1,
  and 64-68 stay the same.
* **Clientbound configuration** (26.2 has 20 packets, 26.3 has 21): `POST_EFFECTS` inserted at **10** [`CFG263` L34. The source comment says
  `0x09`, but the ID is the ordinal, 10]. Ids 10-19 move up by 1, so `CODE_OF_CONDUCT` goes from 19 to 20.
* **Serverbound configuration** is unchanged: both directions use `ServerboundConfigurationPackets1_21_9` (10 packets,
  `ACCEPT_CODE_OF_CONDUCT` = 9) [VV `P263` L281-282; `common/.../v1_21_7to1_21_9/packet/ServerboundConfigurationPackets1_21_9.java`].
* Handshake/status/login: no packet-type mapping for those states in `Protocol26_2To26_3` (only PLAY+CONFIGURATION
  maps are built) [VV `P263` L277-283]. See §E.

## A. Packet bodies that changed

Notation: `VarInt`, `VarLong`, `Bool`, `Byte` (signed i8), `UByte`, `Short` (i16 BE), `Int`, `Long`, `Float`, `Double`,
`String` (VarInt len + UTF-8), `Identifier` (=String), `Position` (i64 packed x26/z26/y12, unchanged),
`UUID` (2×i64), `NBT` (network NBT, unnamed root), `Opt<X>` (Bool prefix + X if true), `OptVarInt`
(**compact**: one VarInt, `0` = absent, otherwise value+1 [VV `TY/OptionalVarIntType.java` L36-48]).
`Holder<X>` = VarInt `id+1`, or `0` followed by an inline X [VV `TY/misc/HolderType.java` L49-65].
`HolderSet` = VarInt `n+1` then n VarInt ids, or `0` then String tag [VV `TY/misc/HolderSetType.java` L56-75].

### A.1 Clientbound PLAY

#### MOVE_ENTITY_POS (26.2: 53/0x35 → 26.3: 54/0x36) ✔✔
| 26.2 | 26.3 |
|---|---|
| VarInt entityId | VarInt entityId |
| Short dx | **VarInt properties** = `(stepCount << 1) \| onGround` |
| Short dy | if stepCount == 0: Short dx, Short dy, Short dz (linear) |
| Short dz | else stepCount × { **VarInt tickOffset**, Short dx, Short dy, Short dz } |
| Bool onGround | (onGround now in bit 0 of properties) |

Sources: Via reads the 26.2 body and writes `(onGround?1:0) | SINGLE_STEP`, then `tickOffset` and the three shorts.
`SINGLE_STEP = 1 << 1` is stepCount 1 [VV `EPR263` L40, L53-64]. tickOffset is estimated from the time between
move packets: 1 if the entity is unknown, if this is its first move, or if more than 5 ticks have passed; otherwise
`round(Δms/50)` with a minimum of 1 [L183-202]. PE: `properties >>> 1` = step count, `properties & 1` = onGround
[PE `WPS/WrapperPlayServerEntityRelativeMove.java` L87-96]. `VecDelta.read`: stepCount ≤ 0 → linear (3 shorts),
otherwise `SteppedVecDelta` [PE `PRO/vector/vecdelta/VecDelta.java` L52-57]. Each step is
`VarInt ticks, Short, Short, Short` [PE `PRO/vector/vecdelta/SteppedVecDelta.java` L46-56, L144-150]. The shorts keep
the 1/4096-block units [PE `VecDelta.java` L34-42].
*A client that only connects through Via always receives stepCount = 1 (properties = 2 or 3).*

#### LIGHT_UPDATE (26.2: 48/0x30 → 49/0x31) and LEVEL_CHUNK_WITH_LIGHT (45/0x2D → 46/0x2E): light masks ✔✔
The 4 BitSets of the light data (skyYMask, blockYMask, emptySkyYMask, emptyBlockYMask) change encoding:
* 26.2: `VarInt longCount + longCount × Long` (i64 BE) per mask (`Types.LONG_ARRAY_PRIMITIVE`
  [VV `T` L169; `TY/LongArrayType.java` L45-50]).
* 26.3: `VarInt byteCount + byteCount × Byte` per mask (`Types.BIT_SET` = `BYTE_ARRAY_PRIMITIVE` of
  `BitSet.toByteArray()` [VV `T` L193; `TY/BitSetType.java` L43-69]). Byte order follows
  `java.util.BitSet.toByteArray()`: little-endian, bit k sits in `bytes[k>>3] >> (k&7)`, and trailing zero bytes are trimmed.
  An empty mask is `VarInt 0`. Conversion from the old form: take each long as 8 little-endian bytes, then trim.

Via: `handleLightMasks` reads 4×LONG_ARRAY and writes 4×BIT_SET [VV `BIR263` L194-199]. LIGHT_UPDATE = `VarInt chunkX,
VarInt chunkZ` + light data [L137-141]. In chunk data it is appended after the chunk + block entities parsed by the shared
`registerLevelChunk1_18` [L142; `common/.../rewriter/BlockRewriter.java` L224-229]. Chunk section format is
unchanged (ChunkType26_1 on both sides) [VV `BPR263` L35]. The sky/block light arrays that follow the masks
are passed through unchanged.
PE: `readChunkMask` → `readByteArray` on ≥26.3 [PE `PRO/world/chunk/ChunkBitMask.java` L28-39].

### A.2 Serverbound PLAY

#### ACCEPT_TELEPORTATION (0/0x00) ✔✔

## E. Connection flow for a 777 client → ViaVersion 5.12.0 → Paper 1.21.11

Pipeline: client 777 → `Protocol26_2To26_3` → 776 → `Protocol26_1To26_2` → 775 → `Protocol1_21_11To26_1` → 774 server.
Everything a 776 client already experiences through Via still applies. For example, 26.2 already has the extra session-UUID
field in LOGIN_FINISHED [VV `common/.../v26_1to26_2/Protocol26_1To26_2.java` L105-111] and a Via-generated
fake player entity id in LOGIN [VV `.../v26_1to26_2/rewriter/EntityPacketRewriter26_2.java` L56-60].

* **Handshake**: same structure. Send protocol version **777**.
* **Status / Login**: no 776→777 change. `Protocol26_2To26_3` registers no LOGIN or STATUS handlers, and its packet maps cover
  only PLAY + CONFIGURATION [VV `P263` L118-175, L277-283]. PacketEvents has no `V_26_3` branch in any login/status
  wrapper (grep of `api/src/main/java` for `V_26_3` lists only play/config/data classes).
* **Configuration**: shift clientbound IDs ≥10 by 1. Expect 2 extra REGISTRY_DATA packets (decorated_pot_pattern,
  block_transformer) right before FINISH_CONFIGURATION (§A.3), and parse the changed registry NBT generically.
  Serverbound config is unchanged. There are **no new required serverbound replies**. ACCEPT_CODE_OF_CONDUCT works as in 776.
* **Play, client obligations that changed**:
  1. ACCEPT_TELEPORTATION must carry pos/rot. Via synthesises the follow-up MOVE_PLAYER_POS_ROT for the server.
  2. Use PUNCH (empty) where a 776 client sent SWING(main hand). 26.3 has no SWING.
  3. PLAYER_ACTION status ids ≥1 go up by 1. Never send 1 (CHANGE_DESTROY_DIRECTION) to a Via/26.2 backend: Via drops it.
  4. SIGN_UPDATE: front/back flag moves to the end.
  5. SPECTATOR_ACTION: new ID, same `OptVarInt` body.
  6. All item component IDs, item IDs, entity types, particle IDs, block states, sounds and argument-parser IDs use the
     26.3 tables (JSON files below).
* **Play, parsing changes**: the entity movement trio + ENTITY_POSITION_SYNC, LOGIN/RESPAWN gamemodes, ANIMATE ids +
  SWING_ANIMATION, LEVEL_PARTICLES reorder, EXPLODE trailing Bool, light-mask BitSets as byte arrays (LIGHT_UPDATE,
  LEVEL_CHUNK_WITH_LIGHT, PLAYER_CHAT filter), UPDATE_ADVANCEMENTS x/y move, OPEN_SIGN_EDITOR slot, recipe tag slot display.
